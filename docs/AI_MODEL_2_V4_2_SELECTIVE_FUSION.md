## 1. Benchmark Metric Integrity Audit

### 1.1 The Mathematical Anomaly in Phase 7F.3
In prior benchmark runs, Candidate Retrieval Recall was reported at $>100\%$. This anomaly arose because candidate matches were tallied across both positive and negative/collision queries but normalized exclusively against the positive query subset ($N_{\text{pos}}$), inflating the calculated ratio beyond unity whenever negative queries retrieved candidates.

### 1.2 Mathematical Formulation of Clean Metric
The candidate retrieval recall is now strictly defined as:

$$\text{Candidate Retrieval Recall} = \frac{\sum_{q \in Q_{\text{pos}}} \mathbb{I}(\text{true\_citizen\_id}(q) \in \text{Candidates}(q))}{|Q_{\text{pos}}|} \times 100\%$$

Where:
- $Q_{\text{pos}}$ is the set of positive queries ($|Q_{\text{pos}}| = 1,500$ in seed `20202`).
- $\text{Candidates}(q)$ is the retrieved set of candidate citizen IDs generated by the identity consolidation candidate pool.
- $\mathbb{I}(\cdot)$ is the indicator function evaluating whether the ground-truth citizen is present in the candidate pool.

### 1.3 Audit Verification
Running `scripts/test-model2-v4-metric-integrity.ts` across edge cases (perfect retrieval, zero retrieval, partial retrieval, negative queries retrieving candidates) proved:
- All recall values are strictly bounded in $[0.0\%, 100.0\%]$.
- Negative and collision queries never contribute to the numerator of positive retrieval recall.
- Clean seed `20202` candidate recall evaluates to **55.27%** (829 true citizen matches out of 1,500 positive queries).

## 2. V4.2 Architecture: Selective Transformer Fusion

```
                           +------------------------------------+
                           |        Incoming Query Text         |
                           +-----------------+------------------+
                                             |
                                  [Language Router]
                                 /         |         \
                                /          |          \
                 [Indic Script]   [Transliterated]    [Standard Latin]
                       |                   |                  |
           (Active Multilingual) (Active Multilingual)  [Structured V3.1 Scorer]
                       \                   /                  |
                        \                 /         (Rule Confidence >= 0.85?)
                         \               /          /                   \
                          \             /         YES                    NO
                           \           /           |                      |
                    +-------v---------v-------+ (Bypass)        (Light Advisory /
                    |   Transformer Scorer    |  W_trans=0.0      Moderate Rerank)
                    | (Multilingual MiniLM)   |                   W_trans=0.10-0.20
                    +------------+------------+                           |
                                 \                                       /
                                  \                                     /
                                 +--v---------------------------------v--+
                                 |         Hybrid Fusion Gater           |
                                 |  - Demographic Conflict Cap (0.25)    |
                                 |  - High Conf Margin Check             |
                                 +-------------------+-------------------+
                                                     |
                                         [Consolidated Person Rank]
```

### 2.1 Language-Aware Router (`language-router.ts`)
Classifies text into one of 5 linguistic domains using Unicode regex ranges and Indic vowel/consonant phoneme token patterns:
1. `ENGLISH`: Standard ASCII/Latin text without Indic phonetic markers.
2. `HINDI`: Devanagari Unicode block (`[\u0900-\u097F]`).
3. `TELUGU`: Telugu Unicode block (`[\u0C00-\u0C7F]`).
4. `TRANSLITERATED_INDIC`: Latin script containing Indic phonetic tokens (e.g., `kumar`, `singh`, `reddy`, `rao`, `sharma`, `devi`, `chandra`, `venkat`).
5. `MIXED`: Multi-script composite tokens.

### 2.2 Selective Gating Decisions (`selective-gater.ts`)
1. **BYPASS_TRANSFORMER** ($W_{\text{trans}} = 0.0$): High-confidence English matches ($\text{Score}_{\text{V3}} \ge 0.85$). Fast-path execution with zero embedding latency.
2. **LIGHT_ADVISORY** ($W_{\text{trans}} = 0.10$): Medium-confidence English matches ($0.60 \le \text{Score}_{\text{V3}} < 0.85$). Provides slight semantic boost without disrupting structural ranking.
3. **MODERATE_RERANK** ($W_{\text{trans}} = 0.20$): Ambiguous English scores or tie-breaks ($\Delta_{\text{score}} < 0.05$). Resolves ambiguous names while retaining demographic anchor.
4. **ACTIVE_MULTILINGUAL** ($W_{\text{trans}} = 0.40$): Hindi, Telugu, or transliterated Indic queries. Employs multilingual semantic embeddings to bridge script differences.
5. **HARD_COLLISION_BLOCK** ($W_{\text{trans}} = 0.0$, $\text{Score} \le 0.25$): Detected demographic conflicts (mismatched DOB, father name, or district). Overrides transformer similarity to prevent false homonym matches.

## 5. Comprehensive Error Analysis

### 5.1 Exact Matches & Initials Handling
- **Performance:** Exact English name queries with standard initials (e.g., `K. Ramesh Kumar` vs `K Ramesh Kumar`) achieve $>98\%$ Top-1 accuracy under V3.1 and V4.2 bypass gating.
- **Root Cause of Misses:** Initials expansion without middle names occasionally maps to multiple sibling records in dense synthetic clusters.

### 5.2 Minor Spelling Variations & Typo Tolerance
- **Performance:** V4.2 selective gating handles single character edit distance errors gracefully via V3.1 Jaro-Winkler + double metaphone fuzzy matching.
- **Benefit:** When V3 confidence drops into the medium band ($[0.60, 0.85)$), the Light Advisory Transformer boost ($W=0.10$) successfully promotes the true candidate without distorting ranking.

### 5.3 Missing / Partial Fields
- **Performance:** Queries lacking `fatherName` or `district` rely primarily on name phonetic similarity.
- **Limitation:** In the absence of father name, Transformer embeddings cannot distinguish homonyms (e.g., two distinct citizens named `Ramesh Kumar` in different wards).

### 5.4 Multilingual Script Queries (Hindi / Telugu)
- **Performance:** Native Indic script queries achieve **14.63%** Top-1 in Hindi and **31.11%** Top-1 in Telugu in V4.2, doubling/tripling V3.1's baseline (**7.32%** and **8.89%**).
- **Residual Bottleneck:** Candidate retrieval recall (stage 1) remains at **55.27%** because candidate generation indexes must also be expanded with Indic phonetic inverted indexes.

### 5.5 Transliterated / Romanized Indic Names
- **Performance:** Romanized Indic queries (e.g., `Reddy` vs `Reddi`, `Chowdary` vs `Choudhary`) reach **58.38%** Top-1 and Top-3 accuracy.
- **Strength:** Phonetic token recognition classifies these as `TRANSLITERATED_INDIC`, activating the multilingual embedding branch.

### 5.6 Homonyms and Same-Name Collision Queries
- **Safety Concern:** For collision queries sharing identical names but having conflicting birth years or father names, V3.1 safely routes 100% of cases to manual review (`Collision FMR = 0.0%`).
- **Transformer Distortion:** In V4.1/V4.2, high semantic similarity between identical names artificially elevates the composite score past the auto-match threshold in 2.9% of collision cases (`Unsafe Automatic Match Rate = 2.9%`).

## 6. Safety Guardrails & Fail-Closed Behavior

1. **Fail-Closed Fallback:** If the Transformer ONNX runtime fails or times out ($>100\text{ ms}$), `v4-engine.ts` immediately falls back to pure V3.1 structured rule scoring without degrading service.
2. **Hard Conflict Capping:** Demographic collision detector caps total composite score at $\le 0.25$ whenever hard demographic mismatch flags are asserted.
3. **No Unsupervised Auto-Match on Collisions:** Production deployment requires $0.0\%$ Unsafe Auto-Match on collision suites. Because V4.2 currently produces $2.9\%$ unsafe matches, it is strictly disqualified from production promotion.
